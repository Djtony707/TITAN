## Gateway authentication and platform webhooks

Source review confirmed that enabled token mode with no configured token bypassed API authentication, while Paperclip management/UI and all-method Ollama proxies ran before the old auth middleware even with authentication configured. One shared boundary now runs before static/body handling or privileged dispatch and protects `/api`, `/v1`, `/ollama`, `/paperclip`, `/mcp` and `/metrics`. Missing, blank or unknown authentication configuration refuses startup; a fresh default token configuration needs private setup. [Gateway setup documentation](gateway-authentication.md) describes masked onboarding and private configuration, without adding an environment binding or putting secrets in shell arguments. Public UI assets/login remain available once startup configuration is valid.

Explicit local no-auth mode requires a loopback effective listener before any network/model/background initialization, including mesh expansion. HTTP and WebSocket requests also recheck that captured listener policy, trusted Host, exact Origin when supplied and cross-site Fetch Metadata. Active network listeners refuse a configuration downgrade to no-auth before persistence. A real bounded `gateway.originAllowlist` schema replaces reliance on an unknown field that configuration parsing discarded. Browser preflights terminate without proxy or operation dispatch; valid local and bearer clients remain supported. Paperclip without a bearer returns 401; gateway credentials, cookies, referrers/original-URL headers and token query parameters are stripped before sidecar forwarding, and upstream redirects are refused.

Exact platform webhook exceptions require their own authentication. Messenger denies missing secrets/signatures and verifies the exact bounded raw JSON bytes; its signing secret remains loaded at adapter connection time, which is not a credential-rotation guarantee. LINE verifies the raw-body HMAC with its configured channel secret as [LINE documents](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/). Twilio denies missing configured Auth Tokens and verifies voice, GET/POST polling and status signatures using the complete URL and POST fields as [Twilio documents](https://www.twilio.com/docs/usage/security). Cached audio retains its bounded random capability/TTL and can contain private speech. Dograh keeps its separate webhook credential; Lark inbound events return an explicit 503 security hold before body parsing until a signing configuration is reviewed. There is no broad `/twilio/*` authentication exemption.

Four real-gateway regressions failed before repair. The final related group passes 169 tests across six files; independent review passes 84. A fresh disposable Chrome profile observed both actual preflights (hostile 403 and authorized 204), zero foreign dispatch, rejected cross-site no-Origin subresources and successful local/bearer requests. No owner browser session, real upstream or provider was used. The first browser fixture used request interception and did not observe preflights; that checkpoint was retained and replaced by the native CORS fixture. The optional MCP HTTP example remains explicitly local/no-auth only, without ambient gateway credentials; built-in authenticated `/mcp` and native stdio retain their separate supported contracts.

## Runtime self-modification security hold

Final source review found that the old apply pipeline trusted mutable `bundle.json` paths, then reread candidate bytes after asynchronous review. Scanning and a model verdict did not bind the approved revision, bytes and target scope. Runtime `applyStagedPR` is therefore unconditionally disabled pending a reviewed replacement. It returns a specific security-hold result before reading bundle metadata or starting a scanner, reviewer, shadow-git snapshot, target copy or archive. Configuration changes, human approval and an approving reviewer cannot override the staged-apply hold. In dedicated self-modification context, disabling staging now refuses direct target writes; ordinary workspace writes are unchanged. This is not a universal filesystem or shell sandbox. Command Post records the approval decision and an error/held episode rather than a merge or completed goal. Staging, manual inspection/export and rejection remain available; automatic application is temporarily unavailable.

Three regressions failed before this containment, then passed for valid candidates, altered outside-target metadata and invalid metadata. They prove unchanged candidate/target bytes, preserved staging, no archival, and no scanner/reviewer/snapshot invocation even with an approving reviewer configured. A separate approval-handler fixture requires truthful held activity and no merged/completed record. Reopening runtime apply requires complete target containment, immutable reviewed bytes and revision-bound human approval; a hash check over mutable paths is insufficient.

The standalone reviewer retains the exact configured model with `noFallback: true`; the legacy prohibited Claude CLI default is not silently replaced. Reviewer settings and verdicts cannot unlock the runtime hold. Scanner secret matches are replaced with `[REDACTED]` when findings are constructed, so serialized findings cannot disclose the matched credential. License identifiers remain available.

Standalone scanner completeness is explicit: .mjs/.cjs/.mts/.cts and other supported text formats are scanned through bounded regular-file descriptors. Missing, unreadable, changing, oversized (>5 MiB), symlink, special or unsupported entries raise typed errors rather than a clean result. Symlinks are rejected before reading external targets; the size check occurs before bounded reading. Only the exact root bundle metadata and listed image/font/media asset formats are excluded, and those paths appear in `excludedFiles`; excluded content is not described as clean. Eleven completeness fixtures cover missing and injected access failures (without uid/chmod assumptions), oversized source, all four added JS/TS extensions, redacted serialization, symlink refusal and explicit asset exclusions. These scans do not authorize runtime application.

## Scheduler, file and encrypted-payload repairs

Cron HTTP and tool controls now use one scheduler/store helper. Disable stops the handle, and queued callbacks recheck the current enabled record and current scheduler handle immediately before shell or model dispatch. A synchronous store save must succeed before an enable/disable success acknowledgment; failed disable stays stopped and reports an error, while failed enable admits no new timer. This prevents a reported-disabled job from returning after an immediate restart. It does not drain work already running. Activity summaries count only exact `active` goal status, so cancelled goals are no longer presented as active.

The authenticated file router previously joined untrusted upload session identifiers to its uploads directory and followed symlinks after lexical validation. Session identifiers are now confined, and fixed file operations execute relative to a policy-selected canonical directory whose device/inode is verified for the request. No-follow descriptors, regular-file/link checks, bounded reads/writes and component identity checks reject traversal, symlinks, special files and controlled path-swap races. Edited-file reads use the same boundary. The helper is supported on Linux/macOS and fails closed elsewhere; same-parent rename is supported, cross-directory rename is refused, and rename is not claimed atomically no-overwrite against other writers. Root identity is pinned per request, not across all future requests. This is a specific API boundary, not a sandbox for the service's generic shell/filesystem authority.

Both session and vault decryptors accepted valid GCM tags truncated to 4/8/12/13/14/15 bytes, allowing a payload modifier to select weaker integrity checking. They now require the existing full 16-byte tag and IV with strict hex/key/salt validation. Saved AES-256-GCM/PBKDF2 format and legitimate roundtrips remain compatible. The synthetic regression suite reproduced shortened-tag acceptance and then passed alongside existing encryption/security/vault tests; no owner secret was read, decrypted or rewritten.
